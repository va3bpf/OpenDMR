# Languages: the design

[中文](i18n.md)

The OpenDMR interface is in English and Chinese today. This is the design for more languages and how to help, for
anyone who wants to translate or work on the code. One rule: **adding a language never removes another one**. All the
languages are built into the firmware and chosen in Options → Language.

## 1. The language number

- Each language has a number: 0 English, 1 Chinese, 2 Spanish, … New ones go at the end; a number never changes.
- The number is kept in OpenDMR's own custom data block of the codeplug (type 0x44540004, "DT" 4), as the key map is
  ("DT" 2). The settings structure `settings_t` must keep the OpenGD77 layout (108 bytes) and has no room left.
- Compatibility: without that block, `bitfield_options` bit 19 set means Chinese, clear English (as stored today).
  Choosing Chinese still sets bit 19, so other CPS see what they saw before.
- The language menu lists every language, each named in its own script (`TEXT_LANGUAGE_NAME`: English, 中文,
  Español, …). When a language's glyphs are not installed (section 3), the menu shows its English name.

## 2. The text tables

- **English is the reference**: the `TEXT_x` of `src/ui/text/text.h` number every string, and the English table has
  them all.
- **One source file per language**: `tools/text/languages/<code>.txt`, UTF-8, one string a line:

  ```
  TEXT_MENU_ZONE = Zona
  TEXT_UI_TX_TIMEOUT = TOT
  ```

  Easier to edit than the windows-1252 C headers of OpenGD77, and no C needed. The existing language files are
  converted to it.
- **`tools/text/gen_text.py` makes `src/ui/text/text_<code>.c`**, and checks:
  - a missing string is written as NULL and `text()` shows the English one, so a new `TEXT_x` never draws nothing;
    the script lists what each language is missing
  - the format specifiers (`%d`, `%s`, …) are the same, in the same order, as in English, or it fails
  - **width**: each string is measured in the firmware's fonts against the room it has on screen (list row names,
    values, bottom bar keys, …), and the ones too wide are listed. Make them shorter: a cut string loses its meaning
- All the languages are built in: about 7 KB each, and the firmware has about 340 KB free, so a dozen or more fit
  without "language packs".
- The generated `.c` is not edited by hand: edit the source file, run the script, commit both.

## 3. Glyphs

Glyphs are found by Unicode code point, not by language: first in the Roboto fonts of the firmware, then in the font
packs of the external flash. So scripts can be mixed, in a channel name too.

| Script | Where | Size |
|---|---|---|
| ASCII | Roboto in the firmware, 9 sizes (today) | 87 KB |
| Latin-1 (the accented letters of Spanish, French, German, Portuguese, …) | Added to Roboto in the firmware | about 20–87 KB |
| Chinese (all of GB2312 at 17 px; level 1 at 32 px bold) | Font pack in the external flash (today's `cjk.bin`) | 2.63 MB |
| Korean (the 2350 common syllables, 17 px) | Font pack in the external flash | about 330 KB |
| Japanese (kana are in GB2312 already; about 1000 Japanese-only kanji, 17 px) | Font pack in the external flash | about 140 KB |
| Arabic (about 300 glyphs) | Font pack in the external flash | about 40 KB |

The font area of the external flash (0x280000 – 0x630000) is 3.69 MB; Chinese uses 2.63 MB, about 1.05 MB is left:
Korean, Japanese and Arabic fit at 17 px; large sizes that do not fit fall back to 17 px (as the Chinese level 2
characters do today).

To do:

- Turn `cjk.bin` into a "font pack" format: each font says its code point ranges, size, weight and, optionally, its
  language; no limit of 4 fonts (`font_cjk.c`, `tools/fonts/mkcjk.py`)
- **Language first**: Chinese and Japanese share the Han code points, and a code point has one glyph. A font pack
  tagged with the interface language comes first, so a Japanese interface shows Japanese forms
- Writing fonts from the CPS (today `tools/fonts/upload_cjk.py`), so users install the packs they want

## 4. Names in the codeplug

Channel, zone and contact names are GB2312, 16 bytes: enough for Chinese, English and Japanese kana, and left as they
are for now. Korean names wait for another encoding (for example the codeplug marked as UTF-8, the CPS converting);
in UTF-8, 16 bytes hold only 5 Korean or Han characters, which the interface and the CPS must say.

## 5. Right-to-left scripts

Arabic and Hebrew run right to left, and Arabic letters change shape with their place in the word. Not now, but kept
possible: all text goes through one function (`font_draw_text()`), where the bidirectional order and the shaping
can go later; mirroring the screens is another step.

## 6. Phases

| Phase | What |
|---|---|
| 1 | The language number and a menu of all languages (section 1); the new source format and the generator's checks (section 2); Spanish added, Chinese kept |
| 2 | Latin-1 in the firmware fonts: the accented letters of Spanish and others |
| 3 | The font pack format and language first; fonts written from the CPS; Korean, Japanese |
| 4 | Right-to-left scripts |

## How to help

- **Translate**: copy the English source file, translate it, run `py tools/text/gen_text.py`, fix what it lists
  (missing, too wide), look at every screen on the radio, and open a PR to `develop`
- **Code**: take the phases in order; say so in an issue before starting, so work is not done twice
- In the PR, say which screens you checked on the radio
