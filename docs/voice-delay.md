# 语音延迟（M17、DMR、NXDN，2026-11-20）

从一台按 PTT 到另一台喇叭出声的时间。通话进行中，延迟也大致就是这么多：放音开始后按实时速度播放，开头积下的
缓冲会一直保持到通话结束。延迟大了，两台离得近时一台说话，另一台像回声。

## 怎么测

调试版固件（`make DEBUG=1`）里的事件日志 `p25_ev`（`src/services/p25_radio.c`，64 条，毫秒时间戳），收发
两端在关键点各记一条（编号见 `tools/debug/voice_delay.py` 开头）。

```sh
py tools/debug/voice_delay.py --tx COM23 --rx COM22 --runs 5 --hold 3
```

脚本先经数据线读两台的节拍计数对齐时钟（取往返最短的一次，误差约 ±4 ms），清空日志，经测试接口按住发射机的
PTT，松开后才读两台的日志，发射期间不碰电台。每次打印两台的事件时间线和"PTT 到第一个声音出喇叭"，以及接收端的
欠载（放音队列空了、放出静音）次数。两台在同一个单频频率、同一模式，刷同一版固件（脚本按 ELF 里的符号地址读
内存），并且是 `make clean` 后编的：增量编译出的几版里，进入 DMR 后第一次发射的话音头对方总收不到（4 次全错），
干净编译后 5 次全对，哪个目标文件旧了没查到（E 盘的文件时间只有 2 秒精度）。

## 结果

| | 改之前 | 改之后（20 次） |
|---|---|---|
| M17 | 314–338 ms | 216–235 ms（中位数 225） |
| DMR（直通，软件收发） | 430–440 ms | 214–233 ms（中位数 224） |
| NXDN48 | 440–614 ms | 289–309 ms（中位数 295） |
| P25（接收改成软件，见 [p25.md](p25.md) 第 5 节） | 250–264 ms | 224–232 ms |

对照：NIST 测的 P25 直通"嘴到耳"延迟约 200 ms（NISTIR 8206）。商用 DMR 没找到公开的数字。

## 时间花在哪里（改之后，中位数）

M17（每 40 ms 一个流帧，两帧 Codec 2）：

| | ms |
|---|---|
| 射频建立 | 38 |
| 第一个流帧进发射队列（40 ms 话筒 + 两次编码） | 54 |
| 前导和 LSF 发完，第一个流帧在队列里等了约 63 ms | |
| 接收端收到 LSF，打开功放 | 137 / 148 |
| 收到第一个流帧 | 178 |
| 攒够（2 帧，再等 25 ms） | 213 |
| 第一个声音（功放启动 85 ms 是现在的瓶颈） | 225 |

DMR（每 60 ms 一个突发，三帧 AMBE+2）：一个话音头，第二帧编好开射频；收到话音头就打开功放，收到第一个突发再等
25 ms 就放。

NXDN48（每 80 ms 一帧，四帧 AMBE+2）：60 ms 引导、前导、VCALL 帧（80 ms），然后语音帧；收到第一个校验通过的帧
（通常是 VCALL 帧）就打开功放，收到第一个语音帧再等 10 ms 就放。

## 改了什么

**放音（`voice_play.c`，三种模式共用）**

- 原来队列里攒够帧（M17 4 帧、DMR 5 帧、NXDN 6 帧）才开始打开功放，功放启动的 85 ms（通路 10 ms + 功放 75 ms）
  里语音继续进队：第一个声音出来时队里已积了 6–9 帧（120–180 ms），一直保持到通话结束。
- 现在通话一开始（M17 的 LSF、DMR 的话音头、NXDN 第一个校验通过的帧）就 `voice_play_prepare()` 打开功放，放静音；
  攒够 `start` 帧、并且离第一帧已过 `start_ms` 才开始放（到达抖动来自录音按块交给软件）。

**录音读取（`p25_phy.c` 的 `afrec_read()`）**

- 调制解调器按 256 个采样（32 ms）一块切换录音缓冲。现在在它写后半块时就把前半块的 128 个采样读出来（换块后
  ≥ 18 ms），软件提前 16 ms 拿到数据，到达抖动也减半，放音前的余量因此可以从 40 ms 减到 25 ms。
- 换块后超过 30 ms 还没看到下一次换块（接收任务被耽误、错过了换块）就不提前读；开机后看到两次换块才开始。
  调试版检查提前读的样本之后有没有变（`afrec_early_mismatch`），约 2 万次检查为 0。`afrec_early` 写 0 可以关掉。

**DMR 发射（`dmr_soft.c`）**

- 话音头 3 个改成 1 个：ETSI TS 102 361-1 第 5.1.2.2 节，常规系统 "a voice LC header shall be sent"，A 突发紧跟其后。
  3 个头让第一个突发在发射队列里多等约 120 ms。
- 第二个 AMBE 帧编好才开射频（`TX_KEY_AFTER`），话音头发出时第一个突发已经编好。只等第一帧时，约 1/12 的通话
  发射队列在头和突发之间空了。
- **发射队列空了奇数块，后面所有突发都会错到另一个时隙**（空的块发成全零，DMR 两个时隙交替）：接收端按话音头对好
  时隙，之后把语音当成另一个时隙的丢掉，整个通话剩下的部分都没声音。现在 `put_burst()` 发现欠载块数是奇数，就补
  一块空的把时隙对回来（`dmr_soft_tx_realigned` 计数）。

**NXDN 接收（`nxdn_radio.c`、`nxdn_core.c`）**

- 通话开始时没有重置超时的起点：VCALL 帧开始的通话被 `poll()` 用上一次通话的时间当场结束，第一个语音帧再开始
  一次（10 次发射算成 14–16 次通话，提前开的功放也被关掉）。
- 锁定条件：原来 LICH 奇偶对（噪声一半能过）、信道类型不是业务信道时连 SACCH 都不查就锁定，空闲时常锁在噪声上；
  对方开始发射时要先失锁（3 帧 240 ms）再重新搜索，VCALL 帧甚至第一个语音帧都漏掉。现在要业务信道并且 SACCH 或
  FACCH1 的 CRC 对；锁定后连续 2 帧 CRC 都不对也重新搜索。
- 搜索：原来第一次超过门限后还要再扫一整帧（80 ms）挑最好的峰；现在只看 4 个符号取峰顶，马上试解，解不出来从那里
  接着搜（采样在环形缓冲里，不会漏）。电脑上 `nxdn/c/run.py` 的 10 段录音结果不变。
- 第一个 SACCH 校验通过的帧就开始通话，不必等 VCALL 解出来（VCALL 帧的 FACCH1 偶尔解不对）；后来读到 VCALL 是
  别人的个呼就结束。

## 还可以做的

- M17：发射端丢掉按 PTT 后最开始约 60 ms 的话筒声音（前导和 LSF 是协议规定的，第一个流帧只能等它们发完），约
  省 60 ms；代价是一按就说时第一个字的开头被吃掉。功放启动 85 ms 现在是 M17 接收端的瓶颈。
- DMR：通话结尾（最后一个超帧放完到收到终止帧之间）偶尔有几十毫秒静音被记成欠载。
- NXDN：解调还是每帧只按同步字定电平，没有 DMR / M17 那样的按判决重估电平和三抽头均衡；弱信号下的效果要用
  弱信号录音量（下一步）。
