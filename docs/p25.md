# P25 Phase 1：电台这一侧

OpenDMR 支持 **APCO P25 Phase 1 常规语音**（直通，组呼，明语）的收发。协议和声码器在子模块 `p25/`
（[p25-core](https://github.com/va3bpf/p25-core)：IMBE 声码器、帧同步、NID、HDU / LDU1 / LDU2 / TDU / TDULC、
Golay / Hamming / Reed-Solomon 纠错）里，与电台无关，可以在电脑上测试。这份文档讲电台这一侧：怎样用 HR_C7000
的“物理层”模式收发 C4FM 符号，以及为此找到的芯片行为。用法见 [使用说明书](manual.md) 第 4 节。

现状：两台 DM-32UV 之间直通、从 HDU 起收发无误；MMDVM 热点（Pi-Star，MMDVM_HS_Dual_Hat）能收到我们的 P25
（BER 0.4%），我们也能收它发的 P25。按键到对方出声约 250–264 ms（DMR 约 340 ms）。已知问题和还没做的
（私呼、加密、中继、Phase 2……）见第 6 节。

依据：HR_C7000 用户手册 v2.7（不在本仓库）“Physical layer reception / transmission”两节，Open25-DM32
（github.com/tylerwatt12/Open25-DM32）公开的文档（只取事实，不用其 GPL 代码），其余都是实测。

## 1. 物理层接收

HR_C7000 除了 DMR 的链路层，还有“物理层”模式：芯片只做 4FSK 解调和同步检测，把判决后的比特交出来，不解 DMR 帧。
P25 的 C4FM 也是 4800 符号/秒的四电平 FSK，映射相同（dibit 01 = +3，00 = +1，10 = −1，11 = −3）。

| 寄存器（基址 0x11000000） | 值 | 含义 |
|---|---|---|
| `WORK_MODE` 0x100 | 0x02 | 物理层，连续模式（0x22 是时隙模式：每 60 ms 只收一个时隙，还会把芯片卡住） |
| `LAYER2_CONTROL` 0x400 | 0x40 | 物理层被动接收 |
| `LAYER2_TXRX_CTRL` 0x408 | 0x41 | 使能接收；先写 0x800000 再写 0x41：回到“等同步” |
| `RECV_MS_SYNC_H/L`、`RECV_BS_SYNC_H/L` | 0x805575F5 / 0x00FF77FF | 同步检测换成 P25 帧同步 0x5575F5FF77FF |

寄存器只能按 32 位读写：按字节写会把调制解调器的寄存器写坏、芯片卡住。

**块**：芯片找到同步以后，每 30 ms 一个系统中断（`SYS_INTERP_LIST` 0x800），从接收 RAM 0x160004E0 起读 36 字节
= 144 个符号。芯片按 DMR 突发的格式重排过这 288 bit（手册 Figure 70，按 `RX_TYPE_INFO` 0x390 低 2 位）：

| 类型 | RAM 里的顺序 | 空中的顺序 |
|---|---|---|
| 0、1 | CACH 24、同步 48、信息 108、信息 108 | CACH 24、信息 108、同步 48、信息 108 |
| 2（带同步的块） | CACH 24、时隙类型 10、时隙类型 10、同步 48、信息 98、信息 98 | CACH 24、信息 98、时隙类型 10、同步 48、时隙类型 10、信息 98 |
| 3 | — | 丢掉 |

排回空中顺序后逐个 dibit 交给 p25-core `p25_rx_dibit()`，它自己找帧同步（不依赖块的边界）、去状态符号、拆帧。
LDU 1728 bit 正好 6 块，HDU 792 bit 不是整块。

**块在空中的位置**（用已知内容的发射逐块对照得出，`p25_radio.c` `place()` 按中断时刻放回原位）：

| 和上一块的间隔 | 含义 | 处理 |
|---|---|---|
| 30 ms | 紧接着的 144 个符号 | 整块 |
| 约 53 ms（找到同步后的第一块） | 中间有 112 个符号芯片没交 | 整块，再补 112 个“删除” |
| 约 7 ms | 锁定中又认到一个同步，插进一个同步块，从上一块的第 32 个符号开始 | 上一块只取前 32 个 |
| 2 块以上 | 断了 | 接收端重新找同步 |
| 内容和上一块一模一样 | 芯片没写这块 | 一块“删除” |

### 1.1 找到同步时丢 112 个符号：纠删补回

芯片从没有信号到找到第一个同步时，交出含同步的那块（同步前 66 到后 77），然后**同步后第 78–189 个符号不交**。
任何发射机都一样，是芯片按 DMR 时隙结构建立接收时隙的结果，寄存器改不掉（试过的见第 6 节）；接收 RAM 整个
1200 字节里也没有这段。

不复位芯片（锁定后它一直交块，信号之间是噪声）时新通话不丢符号，但空闲久了芯片退化：大量填充块（全 +3），新通话
开头几百毫秒误码多。所以每次通话后都复位，每次通话都从没有信号开始锁定，都丢这 112 个符号。

丢的这段正好落在 **HDU** 的数据里（NID 和同步在保住的那块里，LDU1 完整），是 HDU 36 个 RS 符号里的 13 个。接收端
把它当成**删除**（`P25_DIBIT_ERASED`）而不是 0，p25-core 的 Reed-Solomon 做“错误 + 删除”译码
（`p25_rs_decode_erasures()`，2e + 删除数 ≤ n − k），HDU 的 RS(36,20) 能补 16 个；帧层留 2 个校验专门发现纠错出错
（`p25_frame.c` `rs_decode()`）。单元测试：标成删除 200/200 解出、0 次错收；当成 0 时一次也解不出。实测不加前导，
HDU 每次都解出。所以发射**不加前导**，和标准电台一样。

### 1.2 什么时候复位接收（`p25_radio.c`）

- 通话结束后复位
- 芯片交出同步块以后 1 s 没有数据单元（锁在噪声上）：复位
- 芯片一直没交块（在等同步）：每 5 s 复位一次，只防芯片卡住（有一次对方发射中途断掉后，芯片再也找不到同步）。
  原来空闲时每 1 s 复位，会撞上刚找到的同步，7 次通话丢 1 次 LDU
- 开机后第一次找到同步：同步块 30 ms 后多一块接收 RAM 原来的内容（不是空中的），之后的块从同步后第 222 个开始。
  那一块当成删除；这时 HDU 有 16 个删除，留了校验余量就不接受，语音从 LDU1 起不受影响

### 1.3 接收省电

`radio.c` 的接收省电（空闲 12 − 2 × 档位秒后接收机开关轮换）原来只认 FM 载波和 DMR 同步，P25 通话下照样开关，
芯片锁定的信号时有时无。现在 HR_C7000 交出块（找到了同步）就算有动静，省电停下。P25 的帧同步每 180 ms 一个
（DMR 每 60 ms），档位 1 只开 120 ms 时常常一个也看不到（6 次通话 3 次从 HDU 收到，其余晚 260 ms 以上），所以 P25
信道上每次至少开 210 ms，关的时间不变：空闲 15 s 后的 9 次通话都从 HDU 收到。

## 2. 物理层发射

手册只给了寄存器：`WORK_MODE` 0x02、`LAYER2_CONTROL` 0x82、`LAYER2_TXRX_CTRL` 0x81，发送 RAM 两个 36 字节半区
SEND_DATA0（0x16000000）、SEND_DATA1（0x16000024）“交替发送”（手册里这是误码率测试功能）。读取时序都是实测：

1. 芯片轮流读两个半区，每块 30 ms，边发边读
2. 读取用芯片自己的一个定时器：开机后第一次使能发射时启动，之后一直走，停止发射也不停。能看到的中断（发射时隙、
   `phy_rdy`、PCM）每次使能都重新起算，所以和读取的相位关系每次发射都不同
3. **物理层软复位**（`SYS_SOFT_RSTN` 0x11000000 第 1 位写 0 再写 1）让这个定时器从头开始，配置寄存器都不变。每次
   发射前复位后：发射中断在半区 0 的第 10 个符号左右，第 n 次中断时芯片在读半区 n & 1
4. 所以中断 n 时把下一块写进另一个半区 (n + 1) & 1，它要再过约 28 ms 才被读
5. 第一块先写进两个半区，再使能；队列只按整块取，最后的 TDU 补齐到整块
6. 发射时隙中断里不能调用 FreeRTOS（射频任务会坏掉）；关中断时不能靠 `systime_get_us()` 忙等（时间不走，看门狗复位）
7. **发射结束后再软复位一次**：否则调制器停在最后的输出上，之后收到的第一次通话从头到尾约 10% 的符号错，而且只往
   一个方向错（+1→+3、−1→+1、−3→−1）。修之前 8 次里 6 次，修之后 10 次全部正常。（是接收这一台的问题：发射时把
   对方的接收频率调开 20 kHz、对方根本没收到，结果一样。）

写错半区时的样子（定位用）：中断时芯片读到第 p 个符号，p 小时每块前 p 个符号是两块之前的内容；p 大时第 p 个
以后是两块之后的内容，LDU 的帧同步（每块第 108–131 个符号）被覆盖就完全收不到。不复位时 p 每次随机，表现为
“有时全对、有时大面积错、有时收不到”。

## 3. 固件里的结构

- **模式**：`CODEPLUG_MODE_P25`。信道和 VFO 都可以是 P25：码表里按数字信道存（`opendmr_mode` 0xA4，OpenGD77 的
  CPS 显示为 DMR）
- **NAC**：每个信道 / VFO 一个，12 位，默认 293；存在色码字节（`tx_colour`，低 8 位）和 `unused2`（高 4 位，再加
  0xA 作标记；CPS 写的 0x00 / 0xFF 当作没设过，用 293）：`codeplug_p25_nac()` / `codeplug_set_p25_nac()`。只收 NAC
  相同的；F7E（或 F7F）收所有的。别的 NAC 的数据单元计入 `p25_radio_stats.nac_other`
- **通话组**：和 DMR 用同一个发射目标（`tx_target.c`：手动输入的组号、接收组、信道联系人），只发组呼，16 位
  （超出的和个呼：发 TG 1）。HDU 和 LDU1 都写（MMDVMHost 用 LDU1 的）
- **射频前端**：和 DMR 一样（`fd6818_set_dmr()`、频率校准、`receive_on()`），HR_C7000 设成物理层接收，不启动 DMR 引擎
- **中断**：`dmr.c` `system_isr()` 的 P25 分支只读类型和 36 字节进环形缓冲（8 块），通知 P25 任务，中断里不解码
- **接收**（P25 任务）：取块 → 排回空中顺序 → 按时刻放回原位 → `p25_rx_dibit()`；LDU 里每收完一帧 IMBE
  （`p25_rx_ldu_frames()`）就解码，PCM 进 DMR 的放音环（`dmr_sound.c`，预缓冲 80 ms）。HDU / TDU / TDULC 开始、结束
  通话；加密的通话（ALGID 不是 0x80）只显示，语音丢掉
- **发射**：按 PTT 调 `p25_radio_transmit()`：停接收、开麦克风，HDU 进 FIFO，马上开射频；每 20 ms 编一帧 IMBE，
  每编好一帧就把 LDU 里已经确定的部分送进 FIFO（`p25_tx_ldu_ready()`）；松开 PTT 补静音到 LDU2，发 TDU，发完回接收
- **RAM**：P25 不用 AMBE，IMBE 编解码器用同一块 RAM 覆盖区（`.vocoder_overlay`）；P25 任务栈 8 KB（编码器要用）
- **界面**：信道和 VFO 显示 P25、NAC、通话组、源 ID，加密时显示锁；状态栏 `NAC293`；信道详情里 P25 信道的
  “色码”一项是 NAC（十六进制，◀ ▶ 每次 1，按住每次 0x10）

## 4. 和 MMDVM 热点互通

Pi-Star（MMDVM_HS_Dual_Hat，MMDVMHost）收我们发的 P25：`P25, received RF voice transmission … BER: 0.4%`。开始收不到，
原因都在热点那边，记下来给别人参考：

- **热点晶振偏低**（那台低 360 Hz）。它的 ADF7021 用固定门限判四电平，偏 360 Hz 时所有符号往正方向偏一格，数据错
  约 30%，只有只用 ±3 的帧同步还对得上（DMR 同样的频偏只有 2%–3% 误码，不容易发现）。热点 `RXOffset` / `TXOffset`
  校准后 BER 0.4%–0.6%。HR_C7000 自己跟踪频偏，所以热点发、我们收一直正常
- **热点的 ID 库是空的**（`DMRIds.dat` 0 字节，更新失败）：`OverrideUIDCheck=0` 时 MMDVMHost 查不到源 ID 就整个
  通话丢掉，不记日志
- 前导里不能有帧同步：MMDVM 把任何帧同步（错 2 bit 以内）当成帧的开始，接着几个 LDU 都对不上。我们现在不发前导；
  `p25_tx_lead` 可以设成在 HDU 前发 n 块 +3/−3（MMDVM 自己的前导），默认 0

## 5. 延迟

按键到对方喇叭出声（两台的事件日志 `p25_ev`，节拍经数据线对齐）：

| | 按键到出声 |
|---|---|
| 第一版 | 约 650 ms |
| 第一个 LDU 编好 4 帧就开射频 | 约 545 ms |
| 接收每收完一帧 IMBE 就解，不等整个 LDU | 约 460 ms |
| 放音预缓冲 120 → 80 ms（60 一样，40 断续） | 413–416 ms |
| 边编边发，按键就开射频 | 303–304 ms（带 2 块前导） |
| 不发前导（现在） | **约 250–264 ms** |
| DMR（同样测法） | 337–340 ms |

P25 指导委员会的需求说明要求直通 < 250 ms。剩下的：射频建立 30 ms 和 HDU 83 ms 在 LDU1 之前；IMBE 编码器预读约
30 ms；HR_C7000 收发都按 30 ms 一块交接。

## 6. 已知问题（欢迎修改）

每条写了现象、已知的原因和从哪里改起。

**接收**

1. **开机后第一次通话收不到 HDU**：开机后芯片第一次锁定多交一块旧数据（1.2 节），HDU 有 16 个删除，为了留校验
   余量不接受。语音不受影响，只是第一次通话的 HDU 信息（加密参数、HDU 里的通话组）没有。改法方向：弄清开机后芯片
   少做了什么（不是寄存器配置：开机后和第一次通话后寄存器一样），或者用 Golay 软信息把一部分删除变回可信符号
2. **中途进入的通话丢一点语音**：没收到 HDU（信号来晚、刚切到这个频率、省电关着）时，芯片在某个 LDU 的同步上锁定，
   那个 LDU 同步后的 112 个符号同样不交，大约 2 帧语音（40 ms）补不回来（IMBE 帧的纠错码纠不了这么多，解码器按
   错误数重复上一帧）。这是芯片行为，能改的只有让它少发生（见 3）
3. **接收省电时通话开头可能晚一点**：省电关着接收机时，要等下一个开着的窗口里出现帧同步（最多晚一个关闭时长加
   180 ms）。实测空闲 15 s 后 9/9 从 HDU 收到，但没有大量统计。不想要这个延迟可以把信道设成不省电
4. **加密的通话不放音**：只显示加密锁，语音丢掉；没有 DES / AES 解密
5. **只认组呼**：个呼（LCO 3）和其他链路控制格式不按个呼处理；低速数据（LSD）、状态符号都不用；数据
   （PDU、TSDU）不解析
6. **弱信号性能没有量过**：没有做过 BER 随信号强度的曲线，也没和商用 P25 电台对比灵敏度。S 表沿用 DMR 的
7. **没有和商用 P25 电台实测过**：只测过两台 DM-32UV 之间和 MMDVM 热点。改成不加前导以后，还没有再用热点验证一遍
   收我们的信号（理论上更好：热点原来就是被前导里的同步搞错的）

**发射**

8. **按键延迟约 250–264 ms**，比 P25 需求说明的直通 < 250 ms 略多。剩下的时间在射频建立（30 ms）、HDU（83 ms，必须
   先发）、IMBE 编码器预读（约 30 ms）和 HR_C7000 按 30 ms 一块交接
9. **只发组呼、16 位通话组**：个呼、超过 65535 的组号都发成 TG 1；没有紧急呼叫标志；状态符号固定
10. **没有中继 / 集群**：只有普通的收发频率差，没有 P25 中继的上下行处理，没有 Phase 2（TDMA）

**码表和界面**

11. **CPS 不认识 P25 信道**：OpenGD77 的 CPS 把 P25 信道显示成 DMR，NAC 放在色码那个字节和一个保留字节里。在 CPS 里
    改这个信道可能把 NAC 改掉（读回来是 293）。改法方向：我们自己的网页 CPS 支持 P25
12. **NAC 只能在电台上改**（信道详情），通话组用 DMR 的联系人 / 组号，没有单独的 P25 通话组列表

## 7. 调试工具和方法

- `tools/debug/p25_txcheck.py`：两台电台各接一根线（发射 COM14、接收 COM20）。发射方发编号已知的测试帧
  （`p25_tx_source` 1），读接收方的原始块缓存（`p25_tap`），按 `p25/bin/p25_build.exe` 重建的发射内容逐块定位、
  数错误符号，并按在块里的位置统计
- `tools/debug/p25_monitor.py`：在电脑上按同样的规则拼接收方的块、解码，和电台自己解的对照
- `tools/debug/p25_phy.py`：物理层接收捕获、发射测试；`p25_txlog.py`：发射中断日志；`imbe_bench.py`：IMBE 编解码耗时
- 统计：`p25_radio_stats`（块、重复块、数据单元、LDU、LC 错、IMBE 帧和重复帧、复位次数……），`p25_call_log`
- 4×4 混淆表（发的符号 → 收到的符号）很有用：对称的错是噪声 / 定时，单方向的错是频偏或直流
- 一个现象可能来自收发两边时，设计能把两边分开的实验（例如把一台的接收频率调开），不要用互相干扰的实验

### 试过没用的

接收（找到同步时丢 112 个符号）：

| 试的 | 结果 |
|---|---|
| `RF_RECV_DELAY` 0、`LAYER2_SLOT_PRE` 的接收提前量、`REG_X06` | 不变 |
| P25 同步放进 MS / BS / TDMA1 / TDMA2 各组同步寄存器 | 都能检出，丢的一样；RC 组锁不上 |
| 锁定那一刻（同步块中断或其后的时隙中断）写 `TXRX` 0x41 / 0x800041 / 0x40、`LAYER2_CONTROL` 0x41 | 不变 |
| 时隙模式（`WORK_MODE` 0x22）、主动接收（`LAYER2_CONTROL` 0x41） | 只收一个时隙 / 缺口更大，芯片会卡住 |
| 降低同步检测门限（`THRESHOLD_VALUE`） | 不变 |
| 不复位芯片 | 不丢，但空闲久了退化（见 1.1） |

发射（半区的读取时序）：

| 试的 | 结果 |
|---|---|
| 中断里写当前半区 | 每块头部错 |
| 每块写进两个半区 | 数据重复 |
| 中断里忙等再写 | 看门狗复位 |
| `LAYER2_BS_MODE` 基站发射 | 内容全乱 |
| `WORK_MODE` 0x22 时隙模式 | 插入大段空闲符号 |
| `TXRX` 0x80（逐时隙）、使能前写 0x400000 / 0x800000 / 0xC00000 | 相位照样随机 |
| `LAYER2_SLOT_UPDATE` | 只能修 ±1.2 ms |
| `LAYER2_CONTROL` 0x80、0xC2、0xC0、0x83 | 不发射，或收不到且要重启 |
